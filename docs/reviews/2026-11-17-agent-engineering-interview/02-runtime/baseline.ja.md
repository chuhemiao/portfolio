# Agent Runtimeを理解する

ReActとLangGraphを題材に、実行ループ、永続的な承認、冪等性、キャンセル、Replayを面接向けに整理する。

## 1. Agent Loopでタスクを進める

ログインの不具合を直してテストを実行する場合、Coding Agentはプロジェクトを読み、コードを検索し、分析・計画し、編集、テスト、検証、再修正、納品まで進むことがある。モデルを一回呼ぶだけではこの工程を終えられない。各工程の結果を取り込み、定義した完了条件に向けて実行を進めるのがAgent Loopだ。

## 2. ReActとPlan-and-Execute

ReAct（Reasoning and Acting）は観測、判断、ツール実行を繰り返し、結果を次の観測に使う。探索しながら進む作業に向き、方針を変えやすい。呼び出しが増え、同じツールを繰り返したり、局所的な解にとどまったりすることもある。 [ReAct論文](https://arxiv.org/abs/2210.03629)

Plan-and-Executeはレビューできる計画を立ててから実行する。ログインの例なら、構成確認、モジュール特定、原因分析、ファイル修正、テスト、結果検証の六段階になる。依存関係が明確で進捗管理や承認が必要な作業に向く。初期の情報が不十分なら再計画する。全体を計画し、各段階で上限付きのReActを使う方法もある。

## 3. 八段階の実行ループと完了条件

1. 現在のタスク状態を読む。
2. 予算内でコンテキストを組む。
3. モデルから構造化した判断を得る。
4. 判断とツール権限を検証する。
5. 実行するか承認を待つ。
6. ツールの観測結果を保存する。
7. 完了条件を確認する。
8. 未完了なら続けるか再計画する。

完了は観測可能な状態で確認する。モデルが修正済みと答えても、ファイルが変わったか、テストが実行されて通ったか、修正がユーザーのプロジェクトに反映されたかを見る。

## 4. ループの停滞を防ぐ五つの仕組み

1. **予算**。実行回数、トークン、費用、時間、ツールごとの呼び出し数に上限を設ける。
2. **重複検知**。`tool_name + canonical_args + relevant_state` で指紋を作る。新しい観測や状態変更なしに同じ指紋が続けば停滞が疑われる。
3. **進捗検知**。新しい証拠、差分、テスト結果、状態変化を確認する。進まなければ再検討、再計画、機能縮退、人への引き継ぎを選ぶ。
4. **エラー分類**。引数不正、権限エラー、一時的なネットワーク障害は別々に扱う。
5. **安全な終了**。予算枯渇、キャンセル、承認却下、復旧不能にそれぞれ明確な終端状態を設ける。

## 5. LangGraphのState、Node、Edge、Checkpointer

- **State** は実行中のメッセージ、計画、ツール結果、承認、エラー、予算を保持する。
- **Node** はテスト可能な状態変換を行う。コンテキストの組み立て、モデル呼び出し、ツールの準備と実行、結果検証などが該当する。
- **Edge** はノード間をつなぐ。状態に応じて続行、承認待ち、失敗分岐、終了を選べる。
- **Checkpointer** はグラフの位置と再開に必要な状態を保存し、再起動や人の割り込みの後に復旧できるようにする。 [LangGraphの永続化](https://docs.langchain.com/oss/python/langgraph/persistence)

## 6. Checkpoint、業務データベース、実行Journal

フロー状態はグラフの位置を示す。PostgreSQLはタスク、承認、ツール呼び出し、業務イベントを保存する。実行器や外部ツールのJournalには、実際のファイル操作、コマンド実行、副作用の受領記録を残す。

ローカルコマンドでファイルを書き換えた直後に通信が切れると、Checkpointは未完了、業務テーブルは開始済み、Journalは実行済みということがある。再開前に実行状態を照合する。確認せずに再実行すると、副作用が重複し得る。

## 7. 人による承認を永続化する

プロセス内のPromiseは再起動で失われる。承認を業務状態にすると、次のように扱える。

1. Agentが高リスク操作を提案する。
2. 操作種別、対象、引数、差分、根拠、ポリシー版を保存する。
3. タスクを `waiting_approval` にする。
4. Workerの実行リソースを解放する。
5. ユーザーが承認、却下、または提案修正を行う。
6. 承認イベントを保存する。
7. Workerがタスクを再取得する。
8. 実行直前に権限、ファイル版、引数ハッシュ、ポリシー版を再検証する。

許可の対象は特定の提案だ。ファイルや提案の版が変われば改めて承認を得る。LangGraphでは割り込みから再開すると該当ノードの冒頭から再実行するため、割り込み前の副作用も保護する。 [LangGraphの割り込み](https://docs.langchain.com/oss/python/langgraph/interrupts)

## 8. 冪等性、再試行、Exactly Once

決済済みでも応答がタイムアウトすれば、結果は未確認だ。そのまま再試行すると二重請求の恐れがある。リクエストの冪等性は重複送信を、ノードの冪等性は結果の重複を、外部副作用の冪等性は業務処理の重複を防ぐ。

`request_id`、`run_id`、`step_id`、`command_id` を安定した識別子として使う。受領記録がなければ外部状態かJournalを照会し、確認できなければ `outcome_unknown` にする。モデル、DB、ファイルシステム、外部サービスをまたぐ場合は、少なくとも一度の実行割り当て、業務の冪等性、実行記録、不明結果の照合を組み合わせる方が現実的だ。

## 9. キャンセルとReplay

キャンセルは `running` → `cancelling` → 新規ステップ停止 → 実行中の処理にキャンセル要求 → 副作用の照合 → `cancelled` と進む。発生済みの副作用は別途扱い、確認不能なら `outcome_unknown` を残す。

Replayは保存したツール引数と結果を使って、モデルやポリシーのノードを再実行する。変化がモデル、Prompt、ツールSchema、検索結果、ポリシーのどこに由来するかを調べるためだ。実環境のツールを呼び直すと、再課金、重複送信、ファイルの上書きが起こり得る。
