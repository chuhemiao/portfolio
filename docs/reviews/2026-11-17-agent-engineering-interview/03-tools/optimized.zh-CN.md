# Agent 工具工程：MCP、权限与多 Agent

从 Function Calling、MCP 和 Skill 的分工出发，准备工具注册、执行校验、Prompt Injection 防护和多 Agent 协作的面试题。

## 一、工具层决定 Agent 能做什么

模型要查询企业数据库、改文件、提交代码或发起支付，都需要工具层。后端要解决注册与发现、工具选择、参数和权限校验、异常、重复调用、Prompt Injection 防护，以及多个 Agent 怎样共享工具。

## 二、Function Calling、MCP 和 Skill

- **Function Calling** 让模型以结构化参数提出要调用的工具与参数。应用负责实际执行。
- **MCP（Model Context Protocol）** 标准化 AI 应用发现和连接工具、资源及提示模板的方式。
- **Skill** 保存可复用的任务目标、步骤、知识、允许使用的工具、输入输出要求及验收标准。

Skill 可以组织使用多个 MCP 工具，模型通过 Function Calling 表达一次具体调用。Skill 中写明的工具范围需要宿主执行控制。 [Function Calling](https://developers.openai.com/api/docs/guides/function-calling) · [MCP 规范](https://modelcontextprotocol.io/specification/2026-07-28) · [Agent Skills 规范](https://agentskills.io/specification)

## 三、工具按需加载

把几十或数百个工具的说明和 Schema 一次放入上下文，会增加 Token 成本、选择难度和暴露面。可以先按任务和用户权限过滤，再通过目录路由，只加载需要的工具说明与 Schema，执行时重验权限和参数。高频、低风险工具可直接注册，低频工具按需发现。

## 四、Tool Registry 的内容

每项工具至少记录 `tool_id`、版本、描述、输入和输出 Schema、读写级别、资源范围、权限策略、审批策略、超时、重试策略、幂等支持、并发限制、负责人和健康状态。调用时固定版本，避免运行中协议漂移。

跨 Agent 客户端复用可选 MCP。高频且与业务权限紧密绑定的内部工具可以保留类型安全的内部协议。两者可接同一个权限、审计和评测体系。

## 五、后端执行前的五层校验

1. **协议**。检查 JSON、工具注册、Schema、必填字段和类型。
2. **语义**。检查路径、金额、日期、枚举及字段组合是否符合业务规则。
3. **权限**。核对用户、租户、项目、角色及资源授权范围。
4. **策略**。检查操作风险、审批要求、调用次数和累计额度。
5. **执行**。生成稳定调用 ID 和参数指纹，设置超时、幂等、输出上限和审计，再交给隔离执行器。

模型可提出调用。权限由后端判定。

## 六、分类处理错误

工具结果可以包含 `status`、`error_type`、`retryable`、`result_ref`、`partial` 和 `external_receipt`。

- **超时**。只读操作按策略重试，写操作先核验外部状态。
- **空结果**。区分合法为空、权限过滤和上游异常。
- **部分成功**。保存成功与失败项，只重试或补偿安全的子项。
- **脏数据**。校验 Schema、单位、范围和业务不变量。
- **500 错误**。保留上游错误类型及关联 ID，仅重试明确可恢复的错误，持续失败时熔断或降级。

重试受总任务预算约束，使用指数退避和随机抖动。

## 七、在系统层防御 Prompt Injection

例如，外部文档可能夹带把本地文件发往外部地址的要求。上传文件、网页、检索结果和工具返回文本应按不可信数据处理。仅靠 System Prompt 无法保证模型每次都能识别边界。

1. 分开放置系统规则、用户请求、外部数据和工具结果。
2. 标记外部内容不可信。
3. 只暴露当前任务需要的工具。
4. 工具端独立认证并校验权限。
5. 默认只读，高风险写操作要求审批。
6. 限定目录、网络目标及敏感数据访问范围。
7. 在隔离环境中做安全回归测试，验证越权、数据外传及恶意文档能否被拦截。

原稿用 DevPilot 的私有工作副本、目录授权、IPC 白名单、Docker 受限命令及写回审批作例子。它们在执行端约束权限。

## 八、高风险操作的审批与审计

区分读取文件、查知识库和项目等只读操作，编辑私有副本、草稿和临时文件等可逆写入，以及支付、发外部消息、提交正式订单和写生产资源等外部高风险或不可逆操作。

审批界面展示实际操作、目标、关键参数、Diff、依据、可能影响和有效期。按风险级别设置权限和审批。执行前重验授权，执行后保存真实回执。消息、支付和外部提交可能已不可撤销，状态应如实反映。

## 九、何时拆成多个 Agent？

工具和上下文都简单时，单 Agent 通常更便宜，也更容易控制。角色需要不同工具或权限、子任务可并行、上下文须隔离、需要独立验证降低同源偏差或单一上下文过载时，多 Agent 才有价值。

- **Planner** 理解需求并规划。
- **Executor** 调工具、执行工作。
- **Verifier** 独立测试和验证。
- **Supervisor** 分配任务，管理预算、依赖和失败策略，汇总结果。

## 十、共享事实与并发写入控制

共享结构化任务对象，含目标、约束、依赖、确认事实、产物引用和全局预算。局部草稿、临时检索、角色内部执行细节和中间状态由各角色维护。交接至少带 `task_id`、输入版本、输出 Schema、证据引用、完成状态、错误类型及剩余风险。

用 Git commit、文档版本和规则版本固定业务快照。并行编辑优先用独立 worktree 或私有副本，以共同基线做三方合并、冲突检测、测试和审阅。若必须共享锁，用租约和超时限制锁的生命周期，存储端用 fencing token 拒绝过期持有者的写入。
