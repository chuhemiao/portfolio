# Agentのツール設計：MCP、権限、マルチAgent

Function Calling、MCP、Skillの分担から、ツール登録、実行前検証、Prompt Injection対策、マルチAgentの面接論点を整理する。

## 1. ツール層が扱える業務を決める

モデルが社内DBを照会し、ファイルを編集し、コードを提出し、決済を起こすにはツール層が必要だ。バックエンドは登録と発見、選択、引数と権限の検証、例外、重複呼び出し、Prompt Injection対策、複数Agentでの共有を扱う。

## 2. Function Calling、MCP、Skill

- **Function Calling** はツール名と引数を構造化して提案する手段。実行はアプリが担当する。
- **MCP（Model Context Protocol）** は、AIアプリがツール、リソース、プロンプトテンプレートを見つけて接続する方法を標準化する。
- **Skill** は再利用できる目標、手順、知識、利用可能なツール、入出力要件、受け入れ基準をまとめる。

Skillは複数のMCPツールを使う手順を定められる。個別の呼び出しはFunction Callingで表現できる。実際のツールアクセスはホストが制御する。 [Function Calling](https://developers.openai.com/api/docs/guides/function-calling) · [MCP仕様](https://modelcontextprotocol.io/specification/2026-07-28) · [Agent Skills仕様](https://agentskills.io/specification)

## 3. 必要なツールを必要なときに読み込む

数十から数百の説明とSchemaを一度に渡すと、トークン費用が増え、選択が難しくなり、公開範囲も広がる。タスクとユーザー権限で絞り、ツールのカタログで候補を選び、必要な詳細だけを読み込む。実行時は権限と引数を再確認する。頻繁に使う低リスクのツールは直接登録し、利用頻度の低いものは必要に応じて見つける。

## 4. Tool Registryに何を記録するか

`tool_id`、版、説明、入出力Schema、読み書き区分、リソース範囲、権限、承認ポリシー、タイムアウト、再試行、冪等性の対応、同時実行上限、担当者、稼働状態を記録する。実行中に契約が変わらないよう、呼び出し時に版を固定する。

Agentクライアント間で共有するならMCPが候補になる。利用頻度が高く業務権限と密接な内部ツールは型安全な内部プロトコルを維持できる。両方を共通の権限、監査、評価に接続できる。

## 5. 実行前に行う五層の検証

1. **プロトコル**。JSON、登録、Schema、必須項目、型を確認する。
2. **意味**。パス、金額、日付、列挙値、項目の組み合わせを業務ルールと照合する。
3. **権限**。ユーザー、テナント、プロジェクト、ロール、対象リソースの許可範囲を確認する。
4. **ポリシー**。リスク、承認の要否、回数、累積上限を確認する。
5. **実行**。安定した呼び出しIDと引数の指紋を作り、タイムアウト、冪等性、出力上限、監査を設定して分離された実行器に渡す。

モデルは呼び出しを提案し、バックエンドが実行の可否を判定する。

## 6. 失敗を種類ごとに処理する

結果の契約には `status`、`error_type`、`retryable`、`result_ref`、`partial`、`external_receipt` を含められる。

- **タイムアウト**。読み取りはポリシーに従って再試行し、書き込みは外部状態を先に照合する。
- **空の結果**。正当な空、権限フィルター、上流障害を区別する。
- **部分成功**。成功項目と失敗項目を残し、安全な部分だけ再試行または補償する。
- **不正なデータ**。Schema、単位、範囲、業務上の不変条件を検証する。
- **HTTP 500**。上流エラーと相関IDを記録する。復旧できると判断できる場合に再試行し、長引けば遮断するか機能を縮退する。

再試行はタスク全体の予算内で、指数バックオフとジッターを使う。

## 7. Prompt Injectionを実行側でも防ぐ

外部文書に、ローカルのファイルを外部へ送るよう求める文が紛れ込む場合がある。アップロード、Webページ、検索結果、ツールの返答は信頼できないデータとして扱う。System Promptだけで毎回見分けられる保証はない。

1. システムルール、ユーザー要求、外部データ、ツール結果を分けて組み立てる。
2. 外部コンテンツを信頼できないものとして明示する。
3. タスクに必要なツールだけを公開する。
4. ツール側で独立して認証と認可を行う。
5. 既定を読み取り専用とし、高リスクの書き込みに承認を求める。
6. ディレクトリ、通信先、機密データへのアクセスを制限する。
7. 分離環境で越権、外部へのデータ送信、悪意ある文書を遮断できるか回帰テストを行う。

原稿のDevPilotは、私有の作業コピー、ディレクトリ許可、IPCの許可リスト、Dockerで制限したコマンド、元ファイルへの反映の承認を例にしている。これらは実行側で効く制御だ。

## 8. 高リスク操作の承認と監査

ファイル、ナレッジベース、プロジェクトを読む操作と、私有コピー、下書き、一時ファイルへの可逆な書き込みを分ける。決済、外部メッセージ、正式注文、本番リソースへの書き込みには、外部影響や不可逆性がある。

承認には実際の操作、対象、主要引数、差分、根拠、影響、有効期限を表示する。実行直前に再検証し、実行後に本物の受領記録を残す。送信、決済、外部提出が取り消せない場合、その状態を正確に記録する。

## 9. 複数のAgentに分ける条件

ツールとコンテキストが単純なら、単一Agentは費用が低く制御しやすい。役割ごとに権限が違う、タスクを並列化できる、コンテキストを分離したい、独立検証で同じ偏りを減らしたい、単一Agentのコンテキストが飽和している場合に分割する意味がある。

- **Planner** は要求を理解し、計画する。
- **Executor** はツールを呼び出して実行する。
- **Verifier** は独立してテストし検証する。
- **Supervisor** は割り当て、予算、依存関係、失敗時の方針を管理して結果を集める。

## 10. 状態の共有と同時書き込み

共有するタスクオブジェクトに、目標、制約、依存関係、確認済みの事実、成果物参照、全体予算を置く。下書き、一時的な検索結果、役割内部の実行詳細、中間状態は各役割に残す。引き継ぎには `task_id`、入力版、出力Schema、証拠参照、完了状態、エラー種別、残存リスクを含める。

Git commit、文書版、ルール版を固定して同じスナップショットを参照する。並行編集では別worktreeか私有コピーを優先し、共通の基準から三者マージ、競合検出、テスト、レビューを行う。共有ロックが必要ならリースとタイムアウトを設け、保存側がfencing tokenを検査して期限切れの書き込みを拒否する。
