# 第五篇：Production-Grade Agent：评测、可观测性、成本优化与分布式工程实践

## 一、Agent 能够运行，不代表 Agent 能够生产交付

一个 Agent 在本地成功运行一次，并不能证明它已经具备生产能力。

生产环境面对的是持续运行、并发请求、外部服务故障、模型升级、任务中断和数据一致性问题。

因此，生产级 Agent 必须建立完整的工程闭环：

任务执行 → 状态记录 → 结果验证 → 质量评测 → 问题归因 → 系统优化。

本文重点讨论 Agent 从开发环境走向生产环境需要解决的五个问题：

评测、可观测性、成本、基础设施和工程交付。

## 二、如何建立 Agent 评测体系？

传统 LLM 应用往往通过答案质量评估模型。

但 Agent 的结果不只是文本。

例如 Coding Agent 即使给出一段看起来合理的解释，如果代码没有真正修改成功，仍然应该判定为任务失败。

因此，Agent 评测应该拆分为四层。

第一层：模型输出质量。

判断模型的理解、推理和结构化输出是否符合预期。

第二层：工具行为质量。

判断工具选择、参数生成、执行权限和异常处理是否正确。

第三层：流程状态质量。

判断任务是否按照预期完成、暂停、失败或恢复。

第四层：业务结果质量。

判断用户的实际目标是否完成。

这四层不能互相替代。

## 三、Golden Set 应该如何构建？

Golden Set，即黄金评测集，是 Agent 回归测试的基础。

它不应该只是简单的问题和标准答案集合。

对于 Coding Agent，一个完整样本应该包含：

- 固定仓库 Commit。
- 用户原始需求。
- 允许修改的文件范围。
- 禁止执行的动作。
- 必须通过的测试。
- 权限约束。
- 预期结果。

对于 RAG Agent，则应该包含：

- 标准问题。
- 标准证据。
- 文档版本。
- 用户权限。
- 期望引用。
- 正确拒答条件。

还应该覆盖异常场景：

- 工具超时。
- 权限不足。
- 结果为空。
- 多个证据冲突。
- 用户撤权。
- 任务中断。
- Prompt Injection。
- 模型升级后行为漂移。

安全红线不能被平均分抵消。

例如，某个 Agent 的平均任务成功率很高，但出现了越权访问，也不能因此判定它可以上线。

## 四、Trace 是 Agent 系统的黑盒记录机制

如果一个 Agent 最终返回了错误结果，仅仅保存用户输入和最终回答是不够的。

需要知道：

- 模型看到了什么？
- 检索返回了哪些内容？
- 工具选择是否正确？
- 参数是否经过校验？
- 权限是否通过？
- 工具执行是否成功？
- 任务状态如何变化？
- 最终结果如何生成？

因此需要建立完整 Trace。

建议至少关联：

trace_id、user_id、tenant_id、session_id、task_id、run_id、模型版本、Prompt 版本、工具版本、检索候选、Token 用量、工具参数摘要、审批记录、状态迁移、结果引用、错误类型、耗时和成本。

但是，不应该无差别记录密钥、完整敏感文档和所有内部推理内容。

敏感数据应该脱敏，必要正文保存到受控对象存储。

## 五、Replay 为什么重要？

Replay 的价值是复现当时的决策过程。

例如，某次 Agent 任务失败。

我们希望知道问题究竟来自：

- 模型版本。
- Prompt。
- 检索。
- 工具 Schema。
- 权限策略。
- 状态管理。

如果重新执行时再次调用真实工具，外部数据可能已经发生变化，甚至产生新的副作用。

因此，普通 Replay 应冻结当时的工具结果，只重新执行模型和策略节点。

需要进行完整执行测试时，则应该使用独立沙箱和固定数据快照。

两者必须区分。

## 六、如何进行线上坏案例归因？

可以建立以下排查流程：

用户输入 → 检索 → 上下文 → 模型决策 → 工具执行 → 状态变化 → 最终展示。

每一层都应该有对应的观测指标。

例如：

如果检索没有找到正确文档，需要检查解析、Chunk、Query 和索引。

如果检索找到了正确文档，但最终 Prompt 没有包含它，需要检查上下文预算和候选选择。

如果正确证据已经进入上下文，但答案依然错误，就需要检查模型行为、证据冲突和生成约束。

修复后的坏案例应该重新进入 Golden Set，形成持续回归。

## 七、Agent 的延迟和成本应该如何优化？

首先要明确一个指标：

不要只看单次模型调用成本，而应该看完成一个有效业务任务的总成本。

一个 Agent 可能调用模型十次才完成任务，也可能一次调用就成功。

只比较模型单价没有意义。

建议按照任务、模型和执行步骤统计：

- 输入 Token。
- 输出 Token。
- 模型调用次数。
- 缓存命中率。
- 工具调用次数。
- 重试次数。
- 任务成功率。
- 人工接管比例。
- 单任务总成本。

常见优化方式包括：

第一，减少重复上下文。

采用分层摘要、去重和按需加载。

第二，工具延迟加载。

只将当前任务需要的工具 Schema 放入上下文。

第三，模型分级路由。

简单分类和改写任务使用低成本模型，复杂任务再使用高能力模型。

第四，结果缓存。

对 Embedding、解析产物和确定性工具结果进行缓存。

第五，限制执行预算。

控制最大步骤、输出长度和重试次数。

第六，批量处理。

对不需要实时响应的任务进行批处理。

最终应比较单位成功任务成本，而不是单纯追求 Token 数量下降。

## 八、PostgreSQL、Redis、Elasticsearch、Milvus 和对象存储如何分工？

一个 Agent 系统通常需要多种存储。

PostgreSQL：

保存用户、租户、会话、任务、审批、工具调用、规则和审计等强一致业务事实。

Redis：

保存短期缓存、滑动窗口、限流计数、临时通知、短租约和去重标记。

Elasticsearch：

保存全文倒排索引，负责关键词检索、精确术语和过滤。

Milvus 或 PGVector：

保存 Embedding 和向量元数据，用于语义召回。

MinIO 等对象存储：

保存原始附件、解析结果、大型工具输出、报告和不可变快照。

需要注意：

Redis 不能代替业务事实数据库。

向量索引也不能代替最终权限判断。

所有存储都应该通过租户、用户、文档版本和任务 ID 建立关联。

## 九、为什么长任务需要消息队列？

Agent 的任务可能持续数分钟甚至更久。

如果直接在 HTTP 请求中等待模型、文档解析或外部工具执行，容易导致连接超时和服务资源占用。

更合理的方式是：

API 接收请求 → PostgreSQL 保存任务 → 投递消息 → Worker 消费 → 更新任务状态 → SSE 推送进度。

消息队列负责：

- 异步解耦。
- 削峰填谷。
- 任务调度。
- 失败重试。
- 多 Worker 并发处理。

但消息队列不应该替代业务状态机。

消息通常只能保证至少一次投递，因此消费者必须通过事件 ID 或任务步骤 ID 实现幂等。

如果需要数据库与消息发布的一致性，可以使用 Transactional Outbox：

在同一个数据库事务中写入业务任务和待发布事件，再由独立发布器投递消息。

## 十、SSE 如何实现可靠的流式交互？

SSE 是 Agent 系统中常见的流式交互方式。

它适合服务端向浏览器持续推送：

- 模型 Token。
- 工具开始。
- 工具完成。
- 审批等待。
- 任务进度。
- 最终结果。

生产环境需要处理断线重连。

建议每个事件携带：

session_id、run_id、event_id 和递增事件序号。

前端重连时提交最后确认的事件序号。

服务端先返回必要的权威状态快照，再补发后续事件。

模型输出的临时 Token 可以重新构建，但已确认的任务状态和工具执行结果必须以服务端事实为准。

## 十一、Python Asyncio：Agent 为什么需要异步编程？

Agent 系统通常涉及大量 I/O：

- 模型 API。
- 数据库。
- HTTP 服务。
- 对象存储。
- 消息队列。
- 工具调用。

使用 asyncio 可以有效处理这些 I/O 等待。

但需要明确：

asyncio 并不意味着自动并行。

执行 async 函数只会得到 Coroutine，仍然需要 await 或创建 Task。

还需要通过 Semaphore 或有界 Worker Queue 控制并发，防止创建无限任务。

对于不同类型的工作，应该选择不同执行方式：

I/O 密集型：asyncio。

阻塞 I/O：受控线程池。

CPU 密集型：进程池或独立计算服务。

还必须设置连接超时、读取超时和整体任务超时，并正确处理协程取消和资源释放。

取消本地协程并不意味着外部副作用已经撤销。

## 十二、如何解决 Agent 系统的性能问题？

当线上长任务耗时从 5 分钟增加到 20 分钟时，不应该直接认为模型变慢了。

首先需要把整体耗时拆开：

API 排队、Worker 等待、文档解析、检索、模型首 Token、模型总耗时、工具执行、人工等待、数据库查询和前端订阅。

然后比较 P50 和 P95，并检查：

- 队列积压。
- 消费者并发。
- 下游限流。
- 重试放大。
- 数据库慢查询。
- 锁等待。
- 上下文 Token 增长。
- 重复工具调用。

一个项目中的实际优化案例是：

DevPilot 在 RLS 场景下，曾定位命令历史查询扫描大量无关记录的问题。

通过限定 tenant 与已授权运行范围并增加索引，在合成负载中将相关查询从约 0.6 秒优化到约 3 毫秒。

这个结果只代表特定查询场景，不能直接包装成整个 Agent 平台的 P95 性能。

这也是面试时应该具备的数据表达能力。

## 十三、Agent 项目如何从模糊需求走向上线？

业务经常提出：

希望 Agent 更聪明一些。

但这不是可执行的研发需求。

应该先明确：

- 用户是谁？
- 需要解决什么任务？
- 可以访问哪些数据？
- 允许执行哪些工具？
- 什么算任务完成？
- 哪些行为绝对禁止？
- 错误成本是多少？
- 延迟和成本上限是多少？

然后选取 20～50 个具有代表性的案例，定义必须满足、允许差异和拒答条件。

迭代时优先交付最小闭环。

例如：

第一阶段：正确检索资料并给出引用。

第二阶段：增加受控工具调用。

第三阶段：增加人工审批和任务恢复。

第四阶段：增加多 Agent 和复杂任务编排。

每次迭代都应该使用真实坏案例更新评测集。

## 十四、如何判断一个人真正做过生产 Agent？

面试官可以通过以下问题进行判断：

1. 你的 Agent 有多少真实用户和任务量？
2. 任务状态存在哪里？
3. 工具执行一半断网怎么办？
4. 用户撤销权限后，正在运行的任务怎么办？
5. 如何防止重复扣款或重复执行？
6. 如何进行 Replay？
7. 如何构建 Golden Set？
8. 如何追踪线上坏案例？
9. 如何优化单任务成本？
10. 如何保证模型升级后不发生行为漂移？

只会介绍 Prompt、LangChain 或 LangGraph API 的候选人，通常还没有真正理解生产 Agent 的复杂性。

真正有工程经验的人，应该能够解释：

系统发生了什么、为什么发生、如何复现、如何修复，以及如何防止再次发生。

## 十五、结语：Agent Engineering 的竞争力来自系统能力

Agent 技术正在从模型调用层面，逐步转向完整的执行系统工程。

未来真正有价值的 Agent 工程师，不仅需要理解模型和 Prompt，还需要掌握：

- 系统架构。
- 状态管理。
- 工具治理。
- 权限与安全。
- 上下文工程。
- 知识检索。
- 分布式系统。
- 评测与观测。
- 成本与性能优化。

模型决定 Agent 能够提出什么样的决策。

Harness 决定这些决策能否被安全执行。

工程基础设施决定这些执行能否持续、稳定、可验证地交付。

这才是 Production-Grade Agent 的真正含义。
