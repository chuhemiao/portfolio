LLM エージェントの性能はモデルだけで決まるわけではない。過小評価されがちなもう一つの層、harness がある。これはモデルを動かす周辺のシステム層で、システムプロンプト、ツール、記憶、検証規則、オーケストレーション、失敗からの復旧手順を含む。同じモデルでも harness を変えると性能が二倍以上違う場合がある。この事実自体は新しくないが、ますます難しい工学上の問題を生んでいる。モデルごとに失敗の仕方、ツールの使い方、プロンプト形式への感度が異なるため、モデル A に有効な harness がモデル B には最適でないことがある。新モデルの公開速度は手作業の調整が追いつかないほど速くなり、モデルごとに専用 harness を作るコストは制御しにくくなっている。

上海人工智能実験室によるこの論文は、直接的な対処法 Self-Harness を提案する。人間の技術者にも、より強い外部エージェントの指導にも依存せず、エージェント自身に harness を修正させる。これは、強い外部エージェントで弱いエージェントの harness を最適化する従来の Meta-Harness と明確に異なる。Meta-Harness は本質的に外部からの指導である。Self-Harness では改善ループを対象エージェントの内部に取り込み、同じモデルが評価される実行者と変更の提案者を兼ねる。この区別は適用範囲を直接左右する。より強い外部エージェントがない最先端モデルや、外部の指導と対象モデルの失敗の仕方が一致しない場合には、内部化した自己改善が唯一の実行可能な経路となる。

具体的な仕組みは三段階の反復ループである。最初は Weakness Mining。現在の harness で課題群を実行し、失敗した実行履歴を三要素の署名でクラスタリングする。署名は、検証器が最終的に判定した失敗理由、その失敗におけるエージェントの行動の因果的な役割、露呈した抽象的な行動の仕組みを記録する。設計上の要点は、表面的には同じ検証器エラー、例えばタイムアウトでも、背後の行動の仕組みが異なれば同じ群にまとめないことだ。必要な harness の修正が異なるからである。目的は意味の似た失敗を見つけることではなく、同じ harness レベルの介入で解消できる失敗を見つけることにある。

二段階目は Harness Proposal。同じモデルが提案者の役割に切り替わり、まとめられた失敗の証拠から変更候補を生成する。ここでは多様性と最小性という二つの制約を課す。複数の候補は異なる失敗の仕組み、または異なる編集箇所を対象とし、同じ変更の言い換えになってはならない。一つの候補は、その仕組みに必要な部分だけを変え、全体の制御構造には触れないほど狭くする。この制約は、自己改善がシステムプロンプトへの汎用指示の積み上げに流れ、最適化に見えても具体的な問題を解決していない、というよくある失敗に対応している。

三段階目は Proposal Validation。各候補 harness を held-in と held-out の両課題集合で再評価し、どちらも後退せず、少なくとも一方で改善した候補だけを次版へ採用する。この受入規則は保守的である。一方の改善のために他方を悪化させる変更を認めず、そのような候補を見送る。この仕組みは harness の反復を、監査履歴を伴う実証的な過程に変える。各バージョンの遷移には、明確な証拠、変更箇所、評価結果がある。私には性能値そのものより、この監査可能性が重要に思える。自己改善が不透明な漂流ではなく、追跡、再現、必要なら巻き戻しが可能な判断の記録になるからだ。

実験では Terminal-Bench-2.0 上で、異なる系列の三モデル、MiniMax M2.5、Qwen3.5-35B-A3B、GLM-5 を評価した。出発点は意図的に簡素にした harness で、基本的なファイルの読み書き・編集と shell 実行ツール、そして一文のシステム指示だけだった。held-out の合格率は、それぞれ 40.5% から 61.9%、23.8% から 38.1%、42.9% から 57.1% へ上昇し、相対改善率は 33% から 60% だった。注目すべきは改善幅だけではなく、提案時に見ていない held-out 課題で改善したことだ。採用された変更が既知の失敗への暗記的なパッチではなく、再利用可能な実行の仕組みを対象としていることを示す。これは自己改善が汎化しているのか、評価集合に過適合しているだけなのかを判断する核心となる。

三モデルが学んだ変更は互いに異なり、それ自体が中心仮説を支持する。MiniMax M2.5 は、必須ファイルの作成が遅い、構造化ツール出力の扱いが厳密でない、非効率な呼び出しループに陥る、という問題があった。対応する変更は出力ファイルの早期作成、構造化結果の慎重な処理、総ツールメッセージ数の上限による長いループからの転換だった。Qwen3.5 は依存関係を確認せずに作業し、同じ失敗コマンドを繰り返し、探索を延々と続けた。変更は事前の依存確認、失敗コマンドの反復の中断、ツールエラー後に必須ファイルの作成へ戻す注意だった。GLM-5 は shell コマンド間で環境設定が保持されず、探索から実装・テストへの移行が遅かった。変更はセッション間の環境変更の保持と、探索しても必須ファイルが一つもできていなければ実装・検証へ切り替える規則だった。三種類の異なる実行上の問題に三種類の介入を行ったことは、万能の処方を全モデルに適用するよりも、診断に基づく手法であることをよく示している。

ただし、結果の限界も正直に示す必要があり、論文も認めている。第一に、これは閉じたベンチマークでの範囲を限定した harness 編集であり、開放的な自己改善ではない。採用した変更には Terminal-Bench-2.0 固有の特徴が残る可能性があり、全く異なる課題分布でも最適かは不明である。第二に、受入の仕組みは検証器の判定と実行履歴の質に依存する。失敗を合格と誤判定するような体系的な盲点が検証器にあれば、その上に立つ証拠の連鎖も損なわれる。改善を測る物差し自体が独立に検証されていないという、自己参照的なリスクである。第三に、硬い条件は合格件数が減らないことだけだ。資金操作や不可逆な操作を伴う高リスクなエージェントでは、一つのベンチマークで後退しないだけでは変更を許可する根拠として明らかに足りない。論文も、高リスクな変更には合格率の非後退より強い受入条件が必要と述べている。

より大きな視点では、論文の面白さは点数の上昇よりも、harness 工学を手作業の設計から、体系的で監査・再現可能な実証的状態遷移へ再定義したことにある。従来の設計は特定モデルへの技術者の経験と直感に依存し、その経験は蓄積・移転しにくく、モデルが変われば探索をやり直しがちだった。Self-Harness は探索そのものを、証拠と受入規則を伴うループにする。モデル更新がさらに速まれば、一定の harness の適応は、モデル訓練に自動的なハイパーパラメータ探索が欠かせないのと同様、追加の利点から必要条件へ変わるかもしれない。ただし、制御されたベンチマークから本番の適応的 harness へ進むには、検証器の信頼性、リスク段階に応じた受入、課題分布をまたぐ汎化という、まだ十分に解決されていない問題がある。この手法の到達点を決めるのは、現在の数ポイントの改善よりも、それらの問題だろう。
